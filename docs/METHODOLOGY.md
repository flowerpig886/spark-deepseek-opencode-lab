# 测试方法

## 两种 Agent 分开记

2026-11-02 的缓存与思考策略对照主要使用自制固定测试 Agent；2026-11-03 使用已安装的 Windows OpenCode 2.2.5 桌面自带后端，通过 API 创建真实会话、执行真实工具。后者不是 GUI 点击验收，两天不同题和不同 Agent 的成绩不能直接比较。

本轮 OpenCode 使用项目级覆盖/验证工具，流程包括：coverage_plan、check_coverage、workflow_validate、workflow_complete。检查 Agent 自写的测试能否在原始源码上失败、修改后通过，并绑定当前文件版本。它仍然不能保证测试覆盖完整，1050 就出现了“完成回执通过但隐藏测试失败”。本仓库的基础接入示例没有附带该项目专用插件，因此不构成完整流程复现。

## 固定矩阵

| 题目 | 种子 |
|---|---|
| pydicom__pydicom-1033 | 11、23 |
| pydicom__pydicom-1050 | 11、23 |
| pydicom__pydicom-1069 | 11、23 |

题目运行前固定。原计划选择的 marshmallow 题池已用尽，于任何仓库模型运行前改为首三道未用过且测试字段有效的 pydicom 题，按 ID 排序。环境问题修复后仍使用同三题，未按模型表现换题。

每次全新工作区和会话，串行执行；单次最多80次模型调用或20分钟。temperature/top_p 均1，low思考，每请求输出上限32768。种子通过模型请求发送；平台、工具和文件系统因素仍可能影响重跑轨迹。

## 独立判定

- 补丁正确：独立验证侧的指定隐藏验收通过。
- 完整任务：补丁正确，且本轮当前文件验证/覆盖回执通过，并在预算内正常收尾。
- 失败、超时和未完成全部保留，不只报成功样本耗时。
- 隐藏测试、参考补丁仅在验证侧使用，没有送入模型提示或 Windows 模型工作目录。

源代码工作区在 Windows；验证侧在 Spark 的隔离 CPU Docker 容器，显式 runc、无网络、只读挂载、限制CPU/内存。模型容器与测试容器分开。

## 环境有效性

每题先检查：原公开回归通过、缺陷在原代码上复现、参考生产修复在原公开测试与同样隐藏挂载方式下均通过。

旧仓库的 `np.float` 与当前 NumPy 不兼容，在验证进程恢复其历史 builtin-float 别名；原始、参考、候选一致，未要求模型修理环境。元数据中有些公开节点在原始源码不存在：公开检查仅选实际存在的节点，隐藏验收仍保留完整原列表，没有删掉失败要求。

## 连续运行和恢复

连续阶段在新会话中重复固定题，直到至少一小时并完成当前任务。它测服务持续运行，不把重复题当作新质量样本，也不是一条会话持续一小时。

基础恢复分别测主动中断再继续、主动中断后联合重启私有 OpenCode 后端与模型再继续。会话恢复成功和最终补丁正确分别记录。实际生产修改后再中断的补测设置5分钟观察窗口，没有观察到生产修改，按上限结束；不能将这个未进入的恢复环节记作通过。

温度约20秒采样，补测早段存在采样缺口；只报告观测峰值。缓存命中字段与未缓存input分列；输入+cache.read作为包含缓存部分的输入规模观测，不当作上下文极限。

`results/request-metrics.csv`来自已导出的assistant消息，去除了原始会话/消息ID。取消中的请求可能没有完整usage；它不保证与每次传输一一对应。矩阵请求数以本轮请求观察器计数为准。数字导出不包含恢复补测未正常导出的会话，也不包含首次接入小修复；这些分别在报告中记载。
